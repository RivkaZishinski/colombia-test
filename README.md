# אפיון פרויקט APOLO – שלב 2
## רקע כללי
כיום, המערכת רצה על קונטיינר יחיד הכולל חלקי UI וחלקי Server. מטרת הפרויקט היא להפוך את המערכת למבוססת **ארכיטקטורת Microservices**, תוך שיפור ביצועים, תחזוקה וניהול יכולות מתקדמות.
## תכולת המערכת
### קלט לקוח:
- **Route_name** (שם מסלול)
- **Route_path** (מסלול)
- **Control_point** (נקודת שליטה)
- **Route_date** (תאריך המסלול)
- **Location_Error_radius** (רדיוס טעות מיקום)
- **Surface** (משטח)
- **LOS Safety Angle** (זווית בטיחות LOS)
- **LOS Safety Distance Above Peak** (מרחק בטיחות מעל הפסגה)
- **LOS Safety Distance Below Platform** (מרחק בטיחות מתחת לפלטפורמה)
- **Resolution** (רזולוציה)
### פלטים:
- **הפעלת Validate**:
  - מפת מסלול עם שרטוט הנתיב
  - טבלה עם פרטי המסלול
  - שני קבצים המכילים טבלאות המאוחסנות ב-S3
- **הפעלת Generate**:
  - טבלה המאוחסנת ב-S3
## תיאור ממשק משתמש (UI)
### כפתורים במערכת:
1. **Generate**
2. **Validate**
3. **Clean** ( ניקוי שדות )
### תהליך עבודה:
1. לחיצה על **Clean** – מנקה את כלל הפקדים והופכת אותם לריקים.
2. לחיצה על **Validate** או **Generate** – תהליך העבודה מתחיל:
   - **שלב 1:** ביצוע ולידציה של הקלטים.
   - **שלב 2:** אחסון הקלטים והמרתם לפורמט תקין לעיבוד.
   - **שלב 3:** הפעלת פונקציונליות החישוב.
   - **שלב 4:** תוצאה שונה בהתאם לכפתור הנבחר (Generate/Validate).
במקרה של שגיאה, המערכת מציגה הודעת שגיאה מפורטת למשתמש.
## המעבר לארכיטקטורת Microservices
### שירותים במערכת:
1. **Server_Service**: מטפל בבקשות מה-Client, מעבד נתונים ומתקשר עם שאר השירותים.
2. **Client_Service**: אחראי לאינטראקציה עם משתמשי הקצה, שולח בקשות ל-Server_Service.
3. **Los_Map_Service**: מייצר מפת LOS עבור Control Points.
4. **Route_Service**: מייצר מסלולים על בסיס קלט המשתמש.
5. **Redis**: מנגנון Cache לאחסון נתונים על ה-CP.
6. **S3**: אחסון קבצים בענן.
### תיעוד ממשקי API:
התיעוד יבוצע באמצעות **Swagger** לטובת תאימות ותחזוקה קלה.
## תהליכי עבודה עיקריים (Flows)
### מקרה שימוש 1 – יצירת מסלול (נפוץ):
1. המשתמש מזין פרטי מסלול ומבצע ולידציה.
2. המערכת מייצרת חישוב מסלול ומציגה נתונים על המפה.
3. במידה והכול תקין, הנתונים נשמרים ב-S3.
### מקרה שימוש 2 – הוספת Control Point (נדיר):
1. המשתמש מזין פרטי נקודת שליטה.
2. המערכת מעדכנת את מסד הנתונים ואת הנתונים ב-Redis בהתאם לשינויים.
## תיאור שירות ה-UI
### מאפיינים עיקריים:
- שדות קלט לאיסוף נתוני המשתמש.
- פונקציונליות ולידציה לנתונים המוזנים.
- יצירת אובייקט מסלול עם פרטי המסלול (Route_name, Route_path, CP, טריגרים ועוד).
- קריאות API:
  - **ל-Server_Service** לטובת ניהול Redis.
  - **ל-S3** להורדת קבצים.
  - **להפעלת פונקציונליות Validate/Generate**.
### פרטי קריאות API:
- **קריאת POST עבור Validate:**
  - **שולח:** אובייקט מסלול.
  - **מקבל:** סטטוס לתצוגה למשתמש (מבוסס קוד תשובת ה-API).
  - **פלט במקרה של הצלחה:**
    - מסלול בנקודות להצגה על המפה (כולל נתונים מלאים).
    - נתוני הטבלה בפורמט JSON.
    - קישורים לקבצים שהועלו ל-S3.
- **קריאת POST עבור Generate:**
  - **שולח:** אובייקט מסלול.
  - **מקבל:** סטטוס לתצוגה למשתמש.
  - **פלט במקרה של הצלחה:** קישור לקובץ שהועלה ל-S3.
- **קריאת API לנתוני Redis:**
  - **תיאור:** קבלת נתונים מה-Redis.
  - **עדכון דרישות:** הוספת שדה סטטוס משימה (כגון: Working).
## סיכום והמלצות
במעבר לארכיטקטורת Microservices, נדרשת הקפדה על:
- חלוקת אחריות ברורה בין השירותים.
- שימוש ב-Cache (Redis) לצמצום עומסים ושיפור זמני תגובה.
- שימוש ב-Swagger לתיעוד API וניהול תאימות בין צוותים.
### הצעת מבנה עיצובי:
- **Client_Service**: מכיל את ממשק ה-UI וקריאות ל-Server_Service.
- **Server_Service**: פועל כשכבת ביניים לניהול כל הבקשות והתקשורת בין השירותים.
- **Los_Map_Service ו-Route_Service**: שירותים עצמאיים שמנהלים תהליכי יצירת המסלול ומפת LOS.
